Most AI programmes in financial institutions stall at pilot because use cases are picked on value alone. Two questions get asked too late: is the data ready, and can the use case clear Cost, Latency, Accuracy and Security at production scale? Both have answers before the first line of code. The 2x2 below picks where to start. CLAS, my framework for the second question, decides whether a use case can go live.

## Why do AI pilots in financial institutions stall?

I do not have a published stall rate for Indian financial institutions that I would stand behind, so I will not quote one. The mechanism is easier to defend than a statistic, and the public evidence points the same way.

A pilot usually runs on a curated extract, with a small group of users and a forgiving definition of "works". Production has none of those. In the RBI's FREE-AI report, entities named the barriers to wider AI adoption: the talent gap, implementation cost, [lack of high-quality data for model training](https://www.rbi.org.in/Scripts/PublicationReportDetails.aspx?ID=1306), limited compute and legal uncertainty. They also said AI applications are "not plug-and-play". Many found it hard to get domain-specific, structured data out of legacy systems.

On the sensitivity side, the same report notes that most GenAI use cases were still experimental and limited in scope. Entities were reluctant to take customer-facing financial use cases further because of data sensitivity, explainability and bias.

The Bank of England and FCA's 2024 survey of UK firms points the same way. Of the top five perceived current risks, [four were data-related](https://www.bankofengland.co.uk/report/2024/artificial-intelligence-in-uk-financial-services-2024), and data protection and privacy was the largest perceived regulatory constraint. The UK is a different regime, so read it as corroboration of a pattern, not a measure of India.

None of this is a surprise after the pilot. It was knowable before it. That is the claim of this essay.

## Which use cases should start first? A 2x2 of value and data readiness

Put every candidate use case on two axes. **Value** is what the business gains if it works in production. **Data readiness** is whether the data it needs can be reached, trusted and traced today, not after a data programme.

|                | Low data readiness | High data readiness |
| -------------- | ------------------ | ------------------- |
| **High value** | Fix the data first | Ship first          |
| **Low value**  | Park               | Cheap wins          |

**Ship first (high value, high readiness).** Start here and take these straight to the CLAS test below. On Monday, name an owner and a production date.

**Fix the data first (high value, low readiness).** This is the pilot trap, and where most stalls begin. The demo works on a sample, and the value case is real, so it keeps getting funded. On Monday, fund the data work as the project and stop calling it a prerequisite.

**Cheap wins (low value, high readiness).** Do these if CLAS shows they are cheap to run. Do not let them become the programme.

**Park (low value, low readiness).** Say no in writing, so it does not return as a pilot next quarter.

### Where public Indian examples sit

The placements below are my judgement, not findings of the sources.

- **Support, sales and cybersecurity tooling.** In the RBI's survey of 612 supervised entities, 127 were using or developing AI. Across 583 applications in production or development, the most common were customer support (15.6%), credit underwriting (13.7%), sales and marketing (11.8%) and cybersecurity (10.6%). The report says these functions typically involve lower risk, structured flows and easier implementation. That reads as high readiness, and it is a plausible reason they are common.
- **Thin-file credit assessment.** The report sees AI helping assess creditworthiness from non-traditional data for "thin-file" borrowers. Entities also cited sparse data as a bottleneck. High value, historically low readiness.
- **Customer-facing GenAI.** Large potential, but the report records reluctance over data sensitivity. Value is high and readiness, including the security side, is unresolved.

The Account Aggregator framework shows readiness being built as shared infrastructure, outside any one lender. In coverage of a CRIF and Sahamati impact report, [CNBC-TV18](https://www.cnbctv18.com/personal-finance/account-aggregator-led-lending-touches-rs-3-82-lakh-crore-in-fy26-with-no-hit-to-loan-quality-crif-sahamati-report-20012816.htm) cites a Sahamati estimate of ₹3.82 lakh crore of AA-enabled lending across 3.68 crore loans in FY26. As of August 2026 the ecosystem had recorded over 566 million fulfilled consents. Treat the report with care: it is industry-commissioned, and I draw no causal line from AA to credit outcomes. AA is not an AI programme. It is a data-readiness story, which is the point. The FREE-AI report's first recommendation is a [financial sector data infrastructure](https://www.rbi.org.in/Scripts/PublicationReportDetails.aspx?ID=1306), because fragmented, non-standard data makes institutions spend heavy effort on collecting and cleaning before AI can use it.

## What is the CLAS test for going live?

CLAS has four legs, each applied **per use case, not per model**. A model that is fine for one use case can fail another.

- **Cost** with respect to the use case. Does it still make sense at production volume, not pilot volume?
- **Latency or UX** with respect to the use case. Does the response time and experience fit how this use case is actually used?
- **Accuracy** with respect to the use case. How accurate does this particular use case need to be, and what does an error cost here?
- **Security** with respect to the use case. Which data does it touch, and what does the regulation require to process that data in production?

The first three are engineering and economics. Security is where pilots most often hit a wall, because a pilot can quietly use data that production cannot. I split it by data class.

**Public data.** Published circulars, market data, product documents. The constraint is usually reliability and provenance rather than permission, though licence terms still apply.

**Private data.** Internal, confidential, but not personal: policies, pricing logic, internal reports. It is governed by the institution's own controls and contracts. The FREE-AI report flags third-party AI dependencies, where vendors and sub-contractors give an institution limited visibility.

**PII.** The [DPDP Act, 2023](https://www.indiacode.nic.in/bitstream/123456789/22037/1/a2023-22.pdf) defines personal data as data about an identifiable individual. Section 8(5) requires a Data Fiduciary to take reasonable security safeguards to prevent a personal data breach, including for processing by a Data Processor on its behalf. Section 16 lets the Central Government restrict transfers of personal data to notified countries or territories, and says stricter sectoral law still applies.

That last point matters for financial services, because sector rules can be stricter. The RBI's 2018 circular on [Storage of Payment System Data](https://www.rbi.org.in/scripts/NotificationUser.aspx?Id=11244) requires system providers to store the entire payment-system data only in India. The [RBI's FAQs](https://www.rbi.org.in/commonman/english/scripts/FAQs.aspx?Id=2995) add that processing abroad is not barred, but the data must be deleted abroad and brought back to India within one business day or 24 hours, whichever is earlier. A cloud-hosted model that sees payment data is therefore a regulatory question as well as a technical one. Whether the circular applies to a given use case is a question for compliance and legal teams, not this essay. The FREE-AI report itself notes that global AI infrastructure can conflict with data localisation requirements.

## How do the 2x2 and CLAS fit together?

The 2x2 picks where to start. CLAS decides whether the use case can go live.

Use the 2x2 early, when the list is long and you need to choose which three to work on. Use CLAS on the shortlist, and check it before the pilot starts, not after. If a use case clears three legs and fails Security because the data class and the processing rule do not fit, you have learned something that costs nothing now and a quarter later.

It also explains the trap. A high-value, low-readiness use case can fail Security and Accuracy at the same time: data you cannot trust is often data you are not free to move.

## What should a BFSI AI team do on Monday?

1. List your live and planned use cases. The FREE-AI report recommends an internal AI inventory, so this is not wasted work.
2. Place each on the 2x2. Use evidence for readiness: can you reach the data, and can you trace where it came from?
3. For the shortlist, write one line per CLAS leg. For Security, write the data class and the rule that governs processing it in production.
4. Move one high-value, low-readiness use case into a funded data workstream with a named owner.
5. Say no, in writing, to the ones that land in Park.

Do not read this as a guarantee. A use case that clears CLAS can still fail in production, for example if models degrade over time. In the RBI's survey, only 21% of the 127 AI-using entities monitored for data or model drift. Clearing the test earns the right to try. It does not promise an outcome.
